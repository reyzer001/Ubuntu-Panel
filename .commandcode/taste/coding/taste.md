# Taste

- When the user pastes a detailed build/runtime log with "cari tahu errornya dan perbaiki" (find out the error and fix it), they want thorough root-cause discovery of ALL compounding issues, not just the first reported error — this session surfaced six distinct error classes (SWC parse errors, const redeclarations, type errors from a mock meQuery, hardcoded `unlocked` state, structural JSX broken in two regions, and a latent null-vs-undefined type error hidden behind the parse errors). Investigate exhaustively before fixing.
- Diagnostic-first investigation hierarchy before editing: (1) read the target file, (2) check git history (`git log`/`git show`/`git restore`), (3) diff against `.bak` / backup files, (4) inspect build configs (`tsconfig.json`, `package.json`, `eslint`/`eslint.config.*`), (5) grep all usages of affected identifiers, (6) read related files (type/interface definitions, auth store, sibling components) to learn correct patterns — don't guess intent when a reference implementation exists.
- Prefer restoring from version history over reconstructing: try `git restore` → `git show HEAD:...` → `diff file.bak file` to recover the last good version and re-apply intended features; only reconstruct by hand when no history or backup is available.
- Parallelize independent tool calls: batch unrelated reads, greps, and globs in a single message block rather than issuing them sequentially.
- Verify parallel edits by reading back: parallel `edit_file` calls against the same file may race on a stale file snapshot and silently not all apply — always re-read the edited region after to confirm changes actually stuck.
- Build-config-aware cleanup: check `tsconfig.json` for `noUnusedLocals`/`noUnusedParameters` and whether an ESLint config exists before deciding whether unused imports/dead state will fail the build; when they won't, still remove only genuinely-unused symbols (verified via grep) and leave a note about remaining dead stubs for the user to review, rather than silently deleting everything.
- Type-safety verification before reconstructing code: read the relevant type/interface definitions (e.g. `Camera` fields like `credentials`, `rtsp_port`, `stream_path`) and confirm field existence before reconstructing JSX or logic that references typed properties — prevents introducing new type errors.
- When cleaning up a `useState` tuple, check both the value name and the setter name for usages — a value may appear unused via grep while its setter is referenced elsewhere (e.g. in a polling interval or mutation callback). In that case preserve the hook with a hole in the destructuring — `const [, setValue] = useState(init)` — instead of removing the entire hook or leaving an unused value binding. When only the setter is needed, prefer the hole syntax; when neither is used, remove the hook (and any related interval/effect) entirely.
